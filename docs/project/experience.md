# 项目经验

> 不是 bug 清单（那在 build/runtime 两份里），是"怎么做项目"层面的复盘：哪些决策对了、哪些弯路不该走、下次接类似项目怎么开局。

## 1. 走对的路

### 1.1 插件架构从第一天就立住了
品牌协议彼此完全无关（罗技 HID++ / 迈从 0x13 会话 / 雷柏被动心跳），`IBatteryPlugin` 把它们隔进各自文件，DeviceManager 只认接口。事实证明每次动迈从协议，罗技/雷柏零风险；新品牌 = 新文件。**做私有协议集合类工具，第一件事就是把"品牌"变成插件边界。**

### 1.2 "观察 → 抓包 → 单帧验证 → 才写入"的顺序
迈从协议最终 10 分钟打通，靠的不是聪明的猜测，而是顺序对了：
1. 先被动监听（零风险），排除"设备自己会说"的可能；
2. 让**官方软件**去和硬件说话（浏览器 monkey-patch 抓包，见 hardware/debugging.md §1），拿到精确字节；
3. 在独立脚本里发已知帧验证（hidapi，见 hardware/debugging.md §2）；
4. 全部确认后才写进插件。

对比早先的路线：盲扫 255 个命令 × 两轮 → 键盘断连 → 一无所获。**逆向私有协议，信息来源的优先级 = 官方软件 > 公开逆向文档 > 现场猜测。**

### 1.3 日志考古的价值
"邮箱扫描无响应"、"feat8 恒 0x64"这些结论都躺在 app.log 里。动手实验前先 grep 旧日志，几分钟省掉几小时重复劳动。日志里打原始报文 hex 是协议项目的生命线。

### 1.4 安全熔断做进了架构而不是靠自觉
**插件开关即写入授权**（会写帧的插件默认关）、连续 3 次失败自动停写、轮询限频 1 帧/分钟——事故之后这些不是口头承诺，是代码路径。**碰硬件的项目，"最多会发什么"必须是代码可审计的。**

### 1.5 插件架构二次演进（2026-10-05）
三个插件跑通后回看，通用模式（冷却/熔断/生命周期/稳定 Id）在每个插件里重复出现且靠"手动复制"保证——重构沉到 `BatteryPluginBase` 基类 + `DeviceClaimRegistry` 中央认领 + 反射自动发现。时机选择：**等有三个真实实现再抽象**（Rule of Three），抽象出来的是验证过的共性而不是想象中的扩展性；罗技这种会话型不匹配模板就不硬塞，接口 + 共享工具足够。

### 1.6 有争议的小决策复盘
- **自绘图表替代 LiveCharts2**：只要一条曲线，100 行代码换来零依赖，对。
- **GATT 直读替代系统电量属性**：属性名在各 Windows 版本上飘忽，标准 Battery Service 稳定，对。
- **关窗=隐藏托盘**：监控类软件的正确形态，对。
- **历史双通道写入**（变化即写 + 定时采样）：曲线既不漏跳变又连续，对。

## 2. 走过的弯路（成本从大到小）

| 弯路 | 教训 |
|---|---|
| **盲扫硬件命令（255 命令 ×2 轮）** | 不仅危险还零收获。私有协议的命令空间大到扫不出来，正确解法永远是抓官方软件的包 |
| **把"零响应"当协议问题** | dongle 会话被崩溃进程占死时连官方软件都静音。以后先查"谁持有状态/会话"，再怀疑协议（hardware/safety.md §2 事故二） |
| **H.NotifyIcon 引入又移除** | 在 WinUI 3 代码创建场景下事件全失灵。选库前先确认它在"非模板创建窗口"场景有人用过 |
| **XamlCompiler 静默崩溃排查半天** | 写 XAML 属性名时对照官方文档，别凭记忆。崩溃无输出时第一时间怀疑属性名 |
| **跑错输出目录（bin\Debug vs bin\x64\Debug）** | 用旧 exe 验证新代码，浪费一小时。固定：sln 构建 + bin\x64 路径启动 |
| **每个接口都当候选探测** | dongle 的 consumer/system 接口没输出通道，探测它们除了越界崩溃没别的产出。候选过滤先按能力（报告长度）筛 |
| **轻信网上逆向文档的完整性** | mchose-hid-bridge 的 K99 V1 帧格式是对的，但没写"必须先开会话"——差这一条等于全错。文档要验，关键时序要抓包补全 |
| **P/Invoke 一个没验证过存在的导出**（2026-10-06，`HidP_GetReportDescriptor`） | 该 API 在 hid.dll 里**根本不存在**；异常被 catch 吞掉，表现为"设备不支持"，一整天排查方向都是错的。**先证明导出存在，再写解析器** |
| **命名空间取名 `VigilWatt.Core.System`**（2026-10-08，本机电量） | 它在 `VigilWatt.Core` 命名空间树里会**遮蔽 BCL 的 `System`**——同项目里 `System.Threading.Timer`、`System.Text.*`、`System.Runtime.InteropServices` 全部解析失败（CS0234，报错点在其它文件，很迷惑）。教训：**别用框架命名空间做叶子名**（`System`/`Text`/`IO`/`Json` 都危险）；`Enumerable`/`Path` 这类类型名当前缀同理。改用 `Power` 后立即正常 |

## 3. 值得记住的调试直觉

1. **"写入成功但收不到响应"三连查**：会话开了吗 → 悬空读还挂着吗 → 有没有别人抢会话。（本项目三个都中过）
2. **"恒定不变的值"基本不是目标数据**：feat8 的 0x64 0x64 0x64 恒定不变，是配置不是电量。真实电量会在轮询间变化——多读两次对比是便宜的 sanity check。
3. **Windows 的报错码是接口能力探测的免费信息**："参数错误"（WriteFile report ID 不在描述符）、"拒绝访问"（保护 collection）、"函数不正确"（feature 通道不存在）——错误即结论。
4. **多显示器 + DPI 缩放是自动化截图的第一嫌疑**：坐标错位先想 DPI 虚拟化，再想窗口遮挡，最后才想算法。
5. **"用户说点了没反应"先分清"没做"还是"做了但看不见"**：后者更常见也更致命——反馈被自己抹掉、异步没等、重入静默 return，三者叠加能让一个功能正常的按钮看起来完全坏掉。
6. **日志安静 ≠ 卡死**：先看下一轮轮询是否准点开跑，再怀疑死锁。
7. **拿不定字节语义时选保守规则**：宁可漏判、不可误判，并把未定论的口子连同验证方法一起写进文档（hardware/debugging.md §6）。

## 4. 如果重开这个项目（或同类项目）的 checklist

- [ ] 第一天就定插件边界 + 统一设备模型（DeviceStatus 的 Id 稳定性要想清楚，改 Id = 历史断裂）
- [ ] Core 无 UI、日志打原始报文、写入必过开关 + 熔断——这三条做成脚手架而不是事后补
- [ ] 硬件协议：先翻官方驱动支持列表和公开逆向 → 抓包 → 脚本验证 → 插件落地，顺序不可乱
- [ ] HID 读取一开始就用单悬空读模式（这坑每个新 HID 项目都会踩一遍）
- [ ] 托盘/悬浮窗/图表：WinUI 3 生态第三方库质量参差，简单需求自绘/纯 Win32 更可控
- [ ] 每个里程碑用真机验证数值（和键盘指示灯/系统设置页对照），不看日志猜
